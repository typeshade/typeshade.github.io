`§1`부터 `§11`까지는 처음부터 새로 작성하는 사람을 기준으로 구성되어 있습니다. 이 절은
마이그레이션하는 사용자가 실제로 던지는 질문에 답합니다. **내 GLSL 코드가 X를 하는데, DSL
표기는 무엇이고 WGSL에서도 살아남는가?**

이 절이 있는 이유는 실제로 그 검색이 실패했기 때문입니다. 실제 마이그레이션 작업에서는
DSL이 이미 풀어 둔 문제 여러 개를 다시 풀어야 했습니다. 그 이유는 단 하나, 그 기능이
누구도 찾아볼 생각을 못 한 이름으로 등록되어 있었기 때문입니다. 아래 표의 각 행은 적어도
한 번은 손으로 다시 만들어졌던 것들입니다.

| GLSL 구문                                              | DSL 표기법                                  | WGSL 결과                                | 설명                                                                                                                                                                                            |
| ------------------------------------------------------- | -------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uniform Block { … }` (우리 쪽에서 만든 것)              | `uniformStruct` (§4)                         | `@group/@binding var<uniform>`             | std140 레이아웃은 `reflect()`에서 나오므로 오프셋을 직접 세면 안 됩니다                                                                                                                        |
| `uniform float u_x;` (호스트 프리앰블이 선언)            | `externVar`                                  | 같은 참조를, 타깃별 표기로                  | 아무것도 생성하지 않으며, `reflect().requires`에 나타납니다                                                                                                                                        |
| `uniform float u_x;` (우리가 선언하고 호스트가 소유)     | `hostUniform`                                | `@group/@binding var<uniform>`             | GLSL에서는 블록에 속하지 않는 기본 유니폼 하나로 생성되며, `reflect()`는 `owner: 'host'`로 표시합니다                                                                                              |
| 호스트가 소유하는 블록 전체                              | `hostBlock`                                  | `@group/@binding var<uniform>` 하나         | `glsl: 'loose'`는 IR 위에서 이를 멤버별 유니폼 하나씩으로 펼치고 `blk.field`를 `field`로 바꿔 씁니다. 기본값인 `'std140-block'`은 블록을 그대로 유지합니다. WGSL은 어느 쪽이든 블록을 유지합니다. 호스트 바인드 그룹은 하나의 단위이기 때문입니다 |
| 호스트가 제공하는 함수                                   | `externFn`                                   | 같은 호출을, 타깃별 표기로                  | 호출 지점에서 타입이 정해지며, 선언은 생성되지 않습니다                                                                                                                                            |
| `#ifdef FEATURE`: 우리가 결정하는 경우                   | 빌더 매개변수와 평범한 `if` (§11)             | 전처리기 없음                               | 권장 방식입니다. 선택되지 않은 분기는 아예 빌드되지 않으므로 그 바인딩도 선언되지 않습니다                                                                                                          |
| `#ifdef FEATURE`: 호스트가 결정하는 경우                 | `variantFamily`                              | 매트릭스의 각 지점마다 모듈 하나씩           | `emitGuarded`는 define을 소유한 GLSL 호스트를 위해 `#if` 사다리꼴을 생성합니다. 각 분기는 단독 변형과 바이트 단위로 동일합니다. `#include` 안에 들어가는 사다리꼴이 필요하면 `emitGuardedFragment`를 씁니다. 사다리꼴은 같고 프리앰블을 데이터로 돌려준다는 점만 다릅니다 |
| 값 하나만 달라지는 변형                                  | `overrideConst` + `overrideValues` (§11)      | `override` + 파이프라인 상수                | 특수화하면 안 됩니다. 파이프라인만 쓸데없이 늘어나기 때문입니다                                                                                                                                     |
| `#include "helper.glsl"`                                 | `emitGlslFragment` / `emitFragment`          | 호스트가 이어 붙이는 모듈 조각               | `preamble`을 데이터로 돌려줍니다. 정규식으로 헤더를 잘라내지 마십시오                                                                                                                               |
| 모듈 하나 안에 있는 문 수준의 변형 슬롯                   | `composeModule` + `placeholder` (§1)          | 동일                                        | 문 수준의 슬롯만 지원합니다. 상수·구조체·바인딩을 추가하지 않으므로 `#include`를 대신하지 못합니다                                                                                                   |
| 선언 하나에 붙는 `precision highp …`                     | `hostUniform`의 `precision` 옵션              | 해당 없음(WGSL에는 정밀도 한정자가 없습니다) | 스테이지 프리앰블이 기본값이며, 이 옵션은 호스트 프로그램에 합쳐지는 프래그먼트를 위한 것입니다                                                                                                     |
| `usampler2D` / `isampler2D`                              | `texture2duT` / `texture2diT` (§4)           | `texture_2d<u32>` / `texture_2d<i32>`      | 샘플러 정밀도 줄은 자동으로 생성됩니다                                                                                                                                                             |
| `#extension … : require`                                 | `enables` (§10)                              | `enable …;`                                | `capProfile`에 해당 행이 없는 백엔드에서는 (`SD0030`) 안전하게 차단하며 실패합니다                                                                                                                  |
| 옵티마이저 패스를 거친 뒤 두 생성 결과를 비교하는 경우    | `semanticDiff`                               | 동일                                        | IR과 리플렉션을 비교하므로 폴딩이나 이름 변경 때문에 diff가 흐려지지 않습니다. 운영 플러그인을 `transforms`로 선언해 두면 그 재작성 결과는 실패로 잡히는 버킷을 거치지 않고 `explained`로 분류됩니다 (§8) |

### 내장값 어휘: `gl_*` 이름 → WGSL id

`builtin(name, type)`의 어휘는 WGSL의 어휘이며, 타입은 `WgslBuiltinName`입니다. `gl_*` 식
표기나 오타를 쓰면 해당 유니온 타입을 가리키는 `tsc` 오류가 납니다. 이 대응표가 있는
이유는 반대 방향에서 실제로 문제가 났기 때문입니다. GLSL에 익숙한 작성자가 (당시 GLSL
라이터가 받아들이던) `frag_coord`를 썼는데, 모듈은 WGSL 라이터가 돌 때가 되어서야
오류가 났습니다.

**전에는 `frag_coord`가 문제없이 생성되던 버전에서 올라오는 경우라면?** 맞습니다. 다만
GLSL에서만 그랬습니다. 이 별칭은 그 비대칭성 때문에 정확히 폐기되었습니다(#1805). 이
별칭으로 작성한 모듈은 WebGL2에서는 컴파일되고 WGSL에서는 실패했으므로, 상대적으로 덜
테스트하는 타깃에서만 함정이 터졌습니다. 이제 두 라이터 모두 같은 해법으로 이를
거부합니다. 프래그먼트 입력에 `builtin('position', vec4fT)`라고 적으면 됩니다. 이름만
바뀌었을 뿐입니다. GLSL은 여전히 `gl_FragCoord`를 읽고, 생성되는 바이트도 그대로입니다.

| GLSL 전역 변수                    | DSL 표기법                                          | 설명                                                                                                                                                                       |
| ---------------------------------- | ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gl_Position`                      | 버텍스 출력에 쓰는 `builtin('position', vec4fT)`      | GLSL에서는 `gl_Position`을 씁니다                                                                                                                                          |
| `gl_FragCoord`                     | 프래그먼트 입력에 쓰는 `builtin('position', vec4fT)`  | GLSL에서는 `gl_FragCoord`를 읽습니다. y축 원점에 주의해야 합니다. GL 윈도우 좌표는 왼쪽 아래가 원점이고 WGSL 프레임버퍼 좌표는 왼쪽 위가 원점이므로, `.y`를 쓰기 전에 타깃별로 뒤집거나 y 대칭으로 유도해야 합니다 |
| `gl_VertexID`                      | `builtin('vertex_index', u32T)`                       | GLSL에서는 읽을 때 `uint(gl_VertexID)`로 감쌉니다(DSL에서는 u32 타입이지만 GLSL 쪽은 int이기 때문입니다)                                                                     |
| `gl_InstanceID`                    | `builtin('instance_index', u32T)`                     | 마찬가지로 `uint()`로 감쌉니다                                                                                                                                              |
| `gl_FrontFacing`                   | `builtin('front_facing', boolT)`                      |                                                                                                                                                                              |
| `gl_FragDepth`                     | 반환 속성으로 쓰는 `builtin('frag_depth', f32T)`      |                                                                                                                                                                              |
| `gl_PointSize` / `gl_PointCoord`   | 두 라이터 모두 지원하지 않음                          | WGSL이 부족해서 GLSL에 억지로 맞춘 제한이 아닙니다. 포인트 스프라이트는 벤더마다 크기 상한이 다르므로, 맵에서는 인스턴스 쿼드 확장 방식을 택하며 이 내장값들을 아예 제외했습니다(`map/src/shaders/dsl/point.ts`). 생성 오류의 해법도 같은 방식을 안내합니다 |
| float `mod(x, y)`                  | 전역 함수 `mod()`(floor-mod)                          | `.mod()`/`%`는 TRUNC-mod입니다(WGSL 의미론). 이제 GLSL에서도 이식 가능하게 표기할 수 있으므로, 음수에서 어떤 의미를 원하는지에 따라 골라 쓰면 됩니다                          |

**WebGL2만 타깃으로 삼는 경우라면?** 위 내용 중 어느 것도 GLSL 라이터가 표현할 수 있는
범위를 좁히지 않습니다. 중립 이름은 어디까지나 표기법이며, 이 어휘의 규칙 몇 가지는
오히려 WebGL2 출력을 더 명확하게 정의하려고 존재합니다(`round`는 `roundEven`을 생성하고,
float `%`는 GLSL ES 3.00이 실제로 컴파일하는 trunc-mod를 생성합니다). 중립 표면이 다루지
못하는 GLSL 전용 구문에는 `rawStmt` (§1)를 씁니다. 이 함수는 `{ glsl }`만 있는 페이로드를
받아 GLSL 라이터가 그대로 이어 붙이며, 그 모듈에서 WGSL 라이터가 돌아가는 일이 생기면
포팅해야 할 자리를 모두 짚어 (SD0030) 안전하게 차단하며 실패합니다. 오늘은 WebGPU를
배제하지만 앞으로도 계속 그러리라는 보장이 없는 사용자를 위해 의도적으로 이렇게
설계했습니다.

### WGSL에서도 살아남는가?

`capabilityMatrix([wgslBackend, glslEs300Backend])`는 기능별로 이를 답해 주며, 각 백엔드
자신의 `capProfile`에서 직접 끌어온 값이므로 백엔드가 바뀌어도 답이 낡아지지 않습니다.
이 결과가 보고하는 세 가지 지원 등급은 §10에서 설명합니다. 생성이 안전하게 차단되며
실패할 때 `SD0030`의 힌트는 바로 이 절을 가리킵니다.

표의 어떤 행이든 그대로 믿기 전에 알아 두어야 할 사실이 두 가지 있습니다.

- **지원 등급과 실제 사용 가능 여부는 서로 다른 질문입니다.** `f16`, `subgroups`,
  `multiview`는 프로필에 행이 있고 각자의 지시문도 생성하지만, 지금은 셋 다 실제로 작성할
  방법이 없습니다. f16 스칼라도, 서브그룹 내장 함수도 없고, `num_views`도 `gl_ViewID_OVR`도
  없습니다. 매트릭스는 프로필이 말하는 그대로를 보고할 뿐입니다.
  도달할 수 없다고 알려진 기능의 허용 목록은 `capability-reachability.test.ts`에 있으며,
  각 항목마다 이유가 달려 있습니다.
- **행이 빠져 있으면 설계상 완전히 멈춥니다.** 우회할 방법을 알려 주는 힌트가 아닙니다.
  생성 함수는 예외를 던지며, 드라이버가 거부할 소스는 애초에 만들어지지 않습니다.
