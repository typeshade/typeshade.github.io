이 절을 다 읽고 나면 셰이더 안에서 배정밀도 값을 선언하고, 그 값이 어떤 연산을 지원하는지
알고, 에뮬레이션에 필요한 가드 텍스처를 바인딩할 수 있습니다.

GPU에는 64비트 부동소수점 타입이 없습니다. 이 패키지는 `f64`를 에뮬레이션으로 대신합니다.
값 하나를 `f32` 두 개, 곧 상위값(hi)과 하위값(lo)의 쌍으로 나타내고, 실제 값은 이 둘을
합치지 않고 나란히 든 합으로 취급합니다. 그 결과 지수 범위는 f32와 같이 유지한 채, 값이
유지하는 자릿수를 정하는 유효 비트만 약 48비트로 늘어납니다. 1e8에 가까운 값, 예를 들어
월드 좌표 같은 값에서는 f32 한 스텝이 이미 8 단위나 되지만, f64를 쓰면 한 단위보다 훨씬
작은 차이까지 구분할 수 있습니다. 작성 인터페이스는 f32와 같으며, 선언하는 타입만 다릅니다. 생성 전에 실행되는
`fp64Lower` 패스가 모든 f64를 `vec2<f32>`로 바꾸고, 셰이더가 호출할 에뮬레이션 함수를 끼워
넣습니다. WGSL과 GLSL, 그리고 CPU 오라클은 이 계산 결과가 모두 일치합니다.

### f64 값 선언하기

유니폼 필드든, `fn`의 매개변수든, 지역 변수든, `f32T`를 쓰던 자리에 `f64T`를 쓰면 됩니다.
산술 메서드와 비교 연산, 내장 함수는 이름을 그대로 유지하므로, f32로 작성했던 본문을 f64로
바꿀 때 대개 시그니처만 바뀝니다.

```ts
import { f32T, f64T, fn, module, sqrt, toF32, uniformStruct } from '@xgis/shader-dsl'

const U = uniformStruct(
  'U',
  { group: 0, binding: 0, as: 'u' },
  {
    origin: f64T, // one vec2<f32> slot: the host packs splitF64(value)
  },
)

const k = fn('k', { x: f64T, s: f32T }, (p) => toF32(sqrt(p.x.add(U.field.origin).mul(p.s))))
const m = module({ funcs: [k], uses: [U] })
```

모듈 어디에도 fp64를 쓴다고 따로 선언할 필요는 없습니다. 하향 변환 패스가 f64 타입을 스스로
찾아냅니다.

### 변환

f32는 산술 연산 안에서 암묵적으로 f64로 확장되며, 이 확장은 값을 조금도 잃지 않습니다.
`toF64(x)`는 같은 확장을 명시적으로 적는 방법입니다. JavaScript의 숫자는 원래
배정밀도이므로, `f64(1e-9)`나 f64 산술 안에 그대로 쓴 `1e-9`는 빌드 시점에 리터럴을 손실
없이 두 값으로 나눕니다. `f64FromParts(hi, lo)`는 버텍스 속성 쌍처럼 이미 나뉘어 들어온 f32
두 개를 하나의 값으로 조립합니다. 좁히는 변환은 항상 명시적으로 해야 합니다. `toF32(x)`는
hi와 lo를 다시 더해 f32 하나를 돌려주며, 이 과정에서 남은 정밀도를 잃습니다. f64를 정수나
불리언과 섞어 쓰면 작성 시점에 `SD0004` 오류가 됩니다.

```ts
import { f32T, f64, f64FromParts, fn, toF32, toF64 } from '@xgis/shader-dsl'

const g = fn('g', { a: f32T, hi: f32T, lo: f32T }, (p) => {
  const widened = toF64(p.a) // exact
  const lit = f64(1e-9) // split at build time
  const rebuilt = f64FromParts(p.hi, p.lo) // two lanes that were split by the host
  return toF32(widened.add(lit).add(rebuilt)) // the explicit narrow
})
```

### f64가 지원하는 연산

사칙연산 네 가지와 모든 비교 연산, `neg`, `abs`, `min`, `max`, `sqrt`, 보간 계수가 f32인
`mix`, `floor`, `fract`, `sin`, `cos`는 f64 피연산자를 받습니다. 이 목록에 없는 연산을 f64
피연산자에 쓰면 생성 시점에 `SD0041` 오류로 실패하므로, 먼저 `toF32`로 값을 좁힌 뒤 그
부분의 계산을 f32로 마무리해야 합니다. `%`와 비트 연산자는 그보다 앞서 작성 시점에
거부됩니다. `sin`과 `cos`은 주변의 다른 산술 연산보다 정확도가 낮습니다. 이 초월함수
자체의 상대 오차는 아무리 좋아도 약 2^-36 아래로 내려가지 않으며, 인수 축소를 거치면서
인수가 커질수록 오차도 함께 커집니다.

```ts
import { f64, f64T, floor, fn, min, toF32 } from '@xgis/shader-dsl'

// A triangle wave on a coordinate that has outgrown f32.
const stripe = fn('stripe', { x: f64T }, (p) => {
  const y = p.x.mul(0.5)
  const f = y.sub(floor(y))
  return toF32(min(f, f64(1).sub(f)))
})
```

### 가드 텍스처

셰이더 컴파일러는 부동소수점 산술의 결합 순서를 바꿀 수 있는데, 이 재결합은 하필 이
에뮬레이션을 지탱하는 작은 보정 항만 정확히 지워 버립니다. 그래서 생성되는 모든 헬퍼 함수는 컴파일러가
미리 알아볼 수 없는 값, 곧 텍스처에서 읽은 1이라는 값을 그 보정 항 사이로 흘려보냅니다. f64
산술을 쓰는 모듈에는 `_fp64`라는 이름의 `texture_2d<f32>` 바인딩이 그룹 0의 첫 번째 빈
바인딩에 자동으로 끼워 넣어지며, `reflect()`에는 평범한 2D 텍스처로 나타납니다. 호스트는
텍셀 값이 정확히 1.0이 되는 1×1 텍스처를 바인딩해야 합니다. 흰색 RGBA8이든 1.0을 담은
R32F든 상관없습니다. 일부 드라이버는 관찰한 유니폼 값을 기준으로 파이프라인을 특수화해
재최적화하면서 보정 항을 다시 접어 버립니다. 그래서 이 값을 텍스처에 담아 둡니다. 텍셀
값을 상수로 취급하는 컴파일러는 없습니다.

호스트 쪽에서 해야 할 일은 두 가지입니다. 바인드 그룹 레이아웃이 고정되어 있다면 모듈의
`uses`에 `fp64Guard({ group, binding })`를 넣어 슬롯을 고정합니다. Apple GPU에서는
가드만으로 충분하지 않습니다. 플랫폼의 기본 fast math가 어차피 부동소수점 하향 변환을
무너뜨리기 때문입니다. 확인할 수 있는 디바이스 신호를 무엇이든 `recommendFp64Flavor`에 넘기고 그 결과를
생성 시점에 `fp64Flavor`로 건네주면, 이런 기기에서는 가드 바인딩이 아예 필요 없는 정수 기반
하향 변환을 대신 선택합니다.

```ts
// `k` and `U` are the function and the uniform struct from the first example.
import { emitModule, fp64Guard, module, recommendFp64Flavor } from '@xgis/shader-dsl'

const pinned = module({ funcs: [k], uses: [U, fp64Guard({ group: 0, binding: 3 })] })

const flavor = recommendFp64Flavor({ userAgent: navigator.userAgent })
const wgsl = emitModule(pinned, { fp64Flavor: flavor })
```

생성된 셰이더 안에서 이름 공간 두 개는 에뮬레이션이 차지합니다. `df64_`로 시작하는 함수
이름이나 `DF64Vec`, `DF64Mat`으로 시작하는 구조체 이름을 직접 쓰면 생성 시점에 `SD0043`
오류가 됩니다.

### 패킹과 레이아웃

f64 유니폼 필드나 버텍스 속성은 평범한 `vec2<f32>` 슬롯 하나를 차지하며, 크기는 8, 정렬은
8입니다. 호스트에서는 `splitF64(x)`로 값을 패킹합니다. 이 함수는 셰이더가 읽는 순서 그대로
`[hi, lo]` 쌍을 돌려줍니다. 버텍스 스테이지에서 프래그먼트 스테이지로 보간되는 값, 곧
varying은 f64가 될 수 없습니다. 삼각형 위에서 hi/lo 쌍을 보간하면 수치적으로 잘못된 값이
나오기 때문이며, 이는 `SD0044` 오류가 됩니다. 대신 f32 값을 보간하거나, 값을 유니폼으로
넘기고 f64 산술은 프래그먼트 스테이지에서 하십시오.

```ts
import { splitF64 } from '@xgis/shader-dsl'

const [hi, lo] = splitF64(-8_234_567.890123)
new Float32Array(uniformBuffer, 0, 2).set([hi, lo])
```

### 벡터

`vec2f64T`, `vec3f64T`, `vec4f64T`는 벡터 타입이며, `vec2f64(x, y)`와 그 자매 함수들로
만듭니다. 성분 접근과 스위즐, f64·f32·숫자를 브로드캐스트하는 성분별 산술, 성분별 내장
함수 `abs`, `min`, `max`, `mix`, `floor`, `fract`, `sin`, `cos`, `normalize`, 그리고 f64
값을 돌려주는 축약 연산 `dot`, `length`, `distance`까지, 모두 f32 버전과 똑같이 읽힙니다.
이 목록 밖의 연산은 이번에도 `SD0041` 오류가 되므로, `toF32(v.x)`처럼 성분 하나씩
좁혀야 합니다. 벡터는 hi 평면과 lo 평면을 담은 구조체로 하향 변환되므로, 성분별 연산은
벡터 전체에 대해 한 번만 실행됩니다.

```ts
import { dot, f64T, fn, toF32, uniformStruct, vec2f64, vec2f64T } from '@xgis/shader-dsl'

const P = uniformStruct('P', { group: 0, binding: 1, as: 'p' }, { center: vec2f64T })

const d = fn('d', { x: f64T, y: f64T }, (p) => {
  const q = vec2f64(p.x, p.y).sub(P.field.center)
  return toF32(dot(q, q)) // the subtraction and the dot both run in f64
})
```

벡터 유니폼 필드는 구조체 레이아웃을 그대로 차지합니다. 성분이 둘이면 16바이트, 셋이나
넷이면 std140 아래에서 32바이트입니다. 벡터 버텍스 속성은 거부됩니다. hi와 lo를
`vecN<f32>` 위치 두 개로 나눠 전달하고, 레인마다 `f64FromParts`로 다시 조립하십시오.

### 비용

f64 연산 하나는 f32 연산 여러 개에 해당하며, 곱셈이나 덧셈은 열 배 이상 걸리기도 합니다.
그러므로 값 하나 단위로 f64를 쓸지 정해야 합니다. 넓은 범위가 필요한 좌표만 f64로 들고
있다가, 차이가 f32로 감당할 만큼 작아지면 바로 좁히고, 나머지 셰이더는 f32 속도로 실행되게
두십시오.

```ts
import { f64T, fn, toF32 } from '@xgis/shader-dsl'

// The subtraction needs the range; the shading after it does not.
const shade = fn('shade', { world: f64T, camera: f64T }, (p) =>
  toF32(p.world.sub(p.camera)).mul(0.5).add(0.5),
)
```

예제 중 하나인 `examples/fp64-deep-zoom.ts`는 같은 수식을 두 타입으로 나란히 실행해서,
f32 쪽은 평평한 필드로 뭉개지는 반면 f64 쪽은 줄무늬를 그대로 유지하는 모습을 보여줍니다.
