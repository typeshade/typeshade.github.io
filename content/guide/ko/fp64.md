GPU에는 `f64`가 없습니다. DSL은 이를 합치지 않고 따로 든 f32 값 두 개, 곧 **상위값(hi)과
하위값(lo)의 쌍**으로 에뮬레이션합니다. 이 기법을 "더블 플로트"(double-float, df64로도
씁니다)라고 부르며, DSFUN90에서 시작해 NVIDIA CUDA의 `dsadd`/`dsmul`을 거쳐 Thall 계보로
이어져 왔습니다. 그 결과 f32와 같은 지수 범위를 유지한 채 유효 비트만 약 **48비트**로
늘어납니다. 작성 인터페이스는 f32와 완전히 같으며, 선언하는 타입만 다릅니다.

```ts
import { f64T, f64, toF64, toF32, splitF64 } from '@xgis/shader-dsl'

const U = uniformStruct(
  'U',
  { group: 0, binding: 0, as: 'u' },
  {
    origin: f64T, // one vec2<f32> slot — host packs splitF64(value)
  },
)

const k = fn(
  'k',
  { x: f64T, s: f32T },
  (p) => toF32(sqrt(p.x.add(U.field.origin).mul(p.s))), // .add/.mul/sqrt — unchanged syntax
)
const m = module({ funcs: [k], uses: [U] }) // nothing fp64-specific to declare
```

생성 전에 실행되는 `fp64Lower` 패스는 모든 `f64`를 `vec2<f32>`로 바꾸고 `df64_*` 에뮬레이션
호출을 끼워 넣습니다. WGSL과 GLSL, 그리고 JS 숫자를 그대로 쓰는 CPU 오라클(기준값을 내는 CPU
계산)까지 이 값들이 모두 일치합니다. 알아 두어야 할 점은 다음과 같습니다.

- **변환.** `f32 → f64`는 산술 연산 안에서 암묵적으로 확장되며 값을 잃지 않습니다. `toF64(x)`나
  숫자 리터럴을 그대로 써서 명시적으로 확장할 수도 있고, 이 경우 빌드 시점에 두 값으로 손실
  없이 나뉩니다(JS 숫자 자체가 f64이기 때문입니다). 반대로 좁히는 변환은 반드시 명시적으로
  해야 합니다. `toF32(x)`는 hi와 lo를 더한 값을 돌려주며 정밀도를 잃습니다. f64를 정수나
  불리언과 섞어 쓰면 작성 시점에 `SD0004` 오류가 됩니다.
- **지원 연산.** `+ − × ÷`와 모든 비교 연산(사전식 비교), `neg`, `abs`, `min`, `max`, `sqrt`,
  `mix`(보간 계수는 f32), `floor`, `fract`, `sin`, `cos`을 지원합니다. f64 피연산자에 이
  목록에 없는 연산을 쓰면 생성 시점에 `SD0041` 오류를 내며 분명하게 실패하므로, 먼저
  명시적으로 좁혀야 합니다. `%`와 비트 연산은 작성 시점에 거부됩니다.
- **초월함수(`sin` / `cos`).** luma.gl 포트를 기반으로 하며, 3단계로 인수를 축소하고(2π로
  나눈 나머지 → 사분면 → π/16 인덱스), 표로 만든 각도 덧셈을 적용한 뒤 남은 작은 값에 짧은
  테일러 급수를 씁니다. 알아 둘 점은 두 가지입니다. **(1) 정확도**는 산술 연산보다 낮습니다.
  테일러 절단으로 초월함수 자체의 상대 오차는 아무리 좋아도 **~2⁻³⁶** 밑으로 내려가지
  않으며, 인수 축소를 거치면서
  인수 크기가 커질수록 정확도가 더 떨어집니다(이는 큰 인수에서 정밀도가 떨어지는 근본적인
  한계이며, 그래도 f32보다는 훨씬 낫습니다. f32는 인수가 2²⁴를 넘으면 사인 값이 순전한 잡음이
  되는데, f32 인수 자체가 이미 ulp 이하의 위상 정보를 잃었기 때문입니다). **(2) df64_mul의
  제약이 그대로 적용됩니다.** sin/cos은 df64 곱셈 위에 구현되어 있으며, **Apple/Metal**에서는
  이 곱셈이 기본 fast-math 아래에서 무너지는데, 셰이더 안에서 이를 확실하게 막을 방법은
  없습니다(`core/fp64/df64-lib.ts`의 `df64_mul` 관련 설명과 fp64 블로그 Part 7/8을
  참고하십시오). 그래서 곱셈이 살아남는 백엔드에서는 sin/cos이 정확하지만(Blackwell과
  Windows/D3D12 Turing 경로에서 검증했습니다), Apple/Metal에서는 같은 취약점을 그대로
  물려받습니다. 기기 위에서 실행되는 검증 절차는 이 조건을 기기별로 확인할 뿐이며, 모든
  환경에서 정확하다고 보장하지는 않습니다. `vecN<f64>`에도 레인 단위로 같은 규칙이
  적용됩니다.
- **가드 텍스처(자동 삽입).** f64 산술을 쓰는 모듈에는 `texture_2d<f32>` 바인딩이 `_fp64`라는
  이름으로 자동으로 끼워 넣어집니다(그룹 0의 첫 번째 빈 바인딩에 결정적으로 배치됩니다).
  호스트는 텍셀 값이 정확히 1.0이 되는 **1×1 텍스처**를 반드시 바인딩해야 합니다(RGBA8 흰색
  또는 R32F 1.0). WGSL §15.7.5는 재결합을 허용하고 Metal은 기본으로 fast-math를 쓰므로,
  오차 보정 항을 관통하는 런타임 불투명값 `one`이 없으면 그다음 단계의 컴파일러가 df64를
  f32 정밀도로 되접어도 규격상 문제가 되지 않습니다(luma.gl의 CODE_ELIMINATION_WORKAROUND
  계보와 같은 문제입니다). 텍스처를 쓰는 이유는 일부 드라이버가 유니폼 값을 관찰해 파이프라인을
  특수화하고, 항을 접어 버리는 재최적화 변형으로 즉석에서 바꿔치기하기 때문입니다
  (Windows/NVIDIA에서 실제로 관측된 사례입니다). 텍셀 값을 상수로 취급하는 컴파일러는
  없습니다. 엔진이 고정해 둔 바인드 그룹 레이아웃에 슬롯을 맞추려면 `uses:`에
  `fp64Guard({ group, binding })`를 선언하십시오. `_fp64` 선언이 충돌하면 `SD0042` 오류가
  됩니다.
- **레이아웃과 패킹.** f64 유니폼 필드나 버텍스 속성은 평범한 `vec2<f32>` 슬롯을
  차지합니다(크기 8, 정렬 8). `splitF64(x)`로 값을 hi와 lo로 나누어 채웁니다. f64는 버텍스와
  프래그먼트 사이를 보간하는 varying 필드로 쓸 수 없습니다(`SD0044`). hi/lo 쌍을 보간하면
  수치적으로 잘못된 값이 나오기 때문입니다.
- **이름.** `df64_` 함수 접두사와 `DF64VecN` 구조체 이름은 자동 삽입되는 에뮬레이션 코드를
  위해 예약되어 있으므로 직접 선언할 수 없습니다(`SD0043`).
- **비용.** 연산 하나마다 f32 연산보다 몇 배에서 최대 10배까지 비용이 듭니다. 값 하나
  단위로 f64를 쓸지 정하십시오.

### 벡터: `vec2f64T` / `vec3f64T` / `vec4f64T`

`vecNf64(x, y, …)`는 에뮬레이션된 배정밀도 벡터를 만듭니다. 성분(`v.x`), 스위즐(`v.zyx`),
성분별 `+ − ×`(`f64`/`f32`/숫자와 함께 브로드캐스트), `÷`, `neg`, 성분별 내장 함수
`abs`/`min`/`max`/`mix`(보간 계수는 f32)/`floor`/`fract`/`sin`/`cos`/`normalize`, 그리고
축약 연산 `dot`/`length`/`distance`(반환 타입은 `f64`)까지 스칼라와 똑같은 인터페이스를
씁니다. vec64는 `struct DF64VecN { hi: vecN<f32>, lo: vecN<f32> }`로 하향 변환됩니다.
성분별 산술은 hi/lo 평면 전체에 같은 EFT를 한 번에 적용합니다(모든 레인에 twoSum 한 번).
레인마다 분기하는 내장 함수(`abs`, `min` 등)와 `normalize`는 검증된 스칼라 df64 함수를
레인별로 조합해 하나의 `df64_vN_*` 헬퍼 안에 담습니다. `dot`/`length`/`distance`는 스칼라
df64 연쇄를 거쳐 값을 누적합니다. 확장 정밀도로 누적하는 것이 이 설계의 목적입니다.
`sin`/`cos`은 스칼라 df64_sin/df64_cos을 레인별로 조합합니다. vec64에서 이 목록에 없는
연산(`exp`, `clamp` 등)은 모두 `SD0041` 오류가 되므로, 레인별로(`toF32(v.x)`) 먼저
좁혀야 합니다.
vec64 유니폼 필드는 구조체 레이아웃을 그대로 차지합니다(n=2일 때 16 B, n=3/4일 때 std140
아래에서 32 B). vec64 버텍스 속성은 거부되므로(`SD0041`), hi/lo를 `vecN<f32>` `@location`
두 개로 나눠 전달하고(기존 DSFUN 레인 규약과 같습니다) `f64FromParts`로 레인을 다시
만듭니다.

전체 그림은 `examples/fp64-deep-zoom.ts`를 참고하십시오(f32에서는 뭉개지고 f64에서는
줄무늬가 유지되는 모습을 비교할 수 있습니다).
